## Flow documentation

### The flow this task built: web → native app shell

**Purpose.** Ship the Baytos web app as installable iOS and Android
binaries without rewriting the frontend. Capacitor wraps a **static** web
bundle in a native webview, exposes native APIs (camera, biometrics, push)
via TypeScript plugins, and produces standard Xcode / Android Studio
projects that can be signed and submitted to the App Store / Play Store.

**Trigger.** Manual — developer wants to test the app on-device or begin
the App Store / Play Store submission path.

**End.** `out/` (Next.js static export) is copied into both
`ios/App/App/public/` and `android/app/src/main/assets/public/` by
`npx cap sync`. From that point on, opening `ios/App/App.xcworkspace` in
Xcode or `android/` in Android Studio produces a runnable native app.

**Step-by-step sequence executed by this task:**

1. **CocoaPods install** — `brew install cocoapods` (v1.17.0). Pulled in
   Ruby 4.0.6 and openssl@3 3.6.4 as dependencies. Even though Capacitor 8
   iOS uses SPM by default, many community plugins are pod-only, so it's
   worth having installed.
2. **Android Studio install** — `brew install --cask android-studio`
   (Quail 4 2026.1.4.7, arm64). ~1.5GB DMG. Landed at
   `/Applications/Android Studio.app`. The Android SDK itself is **not**
   installed by brew — it's installed by Android Studio's first-launch
   wizard, which the user runs manually.
3. **Capacitor packages in web/** —
   `npm install @capacitor/core @capacitor/cli @capacitor/ios @capacitor/android`.
   103 packages added in 11s from cache (used `--prefer-offline --no-audit
   --fund=false` per the trick documented in the billing-tests doc).
   Landed at `^8.5.1`.
4. **Capacitor init** — `npx cap init "Baytos" "com.baytos.app"
   --web-dir="out"`. Wrote `capacitor.config.ts`. The `--web-dir` flag at
   init time avoids needing a separate edit.
5. **Android platform add** — `npx cap add android`. Scaffolded a full
   Gradle project at `web/android/`. Uses OpenJDK 25 (already installed at
   `/usr/bin/java`). Emitted `sync could not run--missing out directory`
   warning — expected at this point, no build yet.
6. **iOS platform add** — `npx cap add ios`. Scaffolded a full Xcode
   project at `web/ios/`. Uses SPM (`CapApp-SPM/` folder present, no
   `Podfile`). Same missing-out warning.
7. **Server-only Next.js audit** — before touching `next.config.js`,
   grepped for `getServerSideProps`, `generateStaticParams`, `'use server'`,
   `app/api/`, `route.ts`, `middleware.ts`, Prisma/pg/fs imports, and
   `next/image`. All zero matches. Every page is `'use client'` and calls
   the NestJS backend via `NEXT_PUBLIC_API_URL`. Static export is safe.
8. **Enable static export (first attempt)** — added `output: 'export'`,
   `images.unoptimized: true`, `trailingSlash: true` to `next.config.js`.
   `npm run build` failed on `/building/[id]/readings` with
   *"missing generateStaticParams()"* — expected, because the IDs are
   runtime data.
9. **Dynamic-segment refactor (query-string routing)** — moved 7 pages
   from `[id]/*` paths to static paths + `?id=` query. See "Files changed"
   and the routing-decision section below.
10. **Enable static export (second attempt)** — build now failed on all 7
    pages with *"useSearchParams() should be wrapped in a suspense

    Standard Next 14 App Router pattern for CSR pages using
    `useSearchParams` under `output: 'export'`.
11. **Enable static export (third attempt, success)** — `npm run build`

**Databases / tables touched:** none. This is entirely a build-tooling
change plus a client-side routing refactor.

**External calls:** the app continues to call the NestJS backend on
`NEXT_PUBLIC_API_URL` (default `http://localhost:4000`). No change to that
contract. For a device build, this URL will need to point at a
device-reachable IP or a hosted backend — not localhost. Not solved yet.

### Why query-string routing (`?id=`) instead of dynamic segments (`[id]`)

Next.js 14 static export requires that every dynamic route segment
(`app/foo/[id]/page.tsx`) export a `generateStaticParams()` function that
enumerates every valid `id` at **build time**. Our IDs are runtime data —
buildings and bills are created by users, not known at build. Three
options considered:

1. **Query-string routing (chosen).** Move to `app/building/dashboard/page.tsx`
   + read `?id=xyz` via `useSearchParams`. Small, mechanical refactor
   (10 files). Works both inside the Capacitor shell and when the same
   `out/` build is served from a web host. Trade-off: URLs are slightly
   uglier (`/building/dashboard?id=abc` vs `/building/abc/dashboard`).
2. **Remote webview.** Skip static export; point `capacitor.config.ts`
   `server.url` at a hosted URL. **Rejected** — undermines native app
   store review (Apple has been pushing back on apps that are pure
   webviews of a remote site, especially without offline behavior),
   requires network for every launch, and breaks the whole point of
   shipping a native binary. Would also mean maintaining a hosted Next.js
   deployment forever.
3. **Catch-all route + client-side rehydration.** Turn each dynamic
   segment into `[...slug]` with `dynamic = 'force-static'` and parse the
   id out of `usePathname()`. **Rejected** — brittle, Next-specific
   gymnastics, still requires `generateStaticParams` returning something
   non-empty in Next 14's static export mode, and would need special
   handling for the shell nav.

### Known cosmetic tradeoff (flagged for later)
`?id=` URLs look uglier than path segments **if the same Next.js `out/`
build is ever served in a plain web browser** (e.g. someone hits
`baytos.app/building/dashboard?id=xxxxx` in Safari). Inside the Capacitor
shell it doesn't matter — the URL bar is hidden, tenants navigate via
buttons. If we ever ship a browser-facing web version alongside the
native app, this is worth reconsidering (options: a server-rendered
deployment with `[id]` paths that runs alongside the static export, or a
pathname-rewrite trick at the CDN edge).

### The Suspense-wrapper pattern (why every page has a `Page()` and an inner)
Each of the 7 refactored pages now looks like:
```
export default function Page() {
  return <Suspense fallback={null}><Foo /></Suspense>;
}
function Foo() {
  const id = useSearchParams().get('id') || '';
  ...
}
```
This is Next 14's requirement, not a stylistic choice: `useSearchParams`
must be inside a Suspense boundary in App Router pages under `output:
'export'` or the build errors with `missing-suspense-with-csr-bailout`.
`fallback={null}` is fine because the render below shows its own empty /
loading state anyway (each page has an `if (!data) return ...` guard).

**Branching / edge cases:**
- `id` missing from URL — `useSearchParams().get('id')` returns `null`;
  coerced to empty string. Every page's `useEffect` is guarded on `if (id)`
  so no API call fires with an empty ID. UI shows the empty state.
- Deep links from outside the app (e.g. push notifications) — should be
  formatted as `/building/dashboard?id=xxx`, not the old `/building/xxx/
  dashboard`. Not implemented yet, but if we add push, this is the shape.

## Notes

### Bundle ID
Chose `com.baytos.app`. Reasonable placeholder; if Baytos later takes
ownership of a specific domain, App Store / Play Store convention is
reverse-DNS of the owned domain (`io.baytos.app`, `co.baytos.app`, etc.).
Changing the bundle ID after store submission is very painful (regenerated
native projects, new provisioning profiles, new Firebase config, users
can't upgrade in place). Worth confirming the domain choice before the
first TestFlight upload.

### Android Studio: manual step remaining
Brew installs the `.app` but not the SDK. User must:
1. Open Android Studio.app.
2. Complete the first-launch wizard (SDK install, downloads ~2-3 GB into
   `~/Library/Android/sdk`).
3. Optionally install an emulator image (Pixel 8 API 34 is a fine
   default).

Until then, `web/android/` exists but can't build. iOS should work now:
open `web/ios/App/App.xcworkspace` in Xcode, select a simulator, hit Run.

### Capacitor 8 uses SPM, not CocoaPods, for iOS
`web/ios/App/` has no `Podfile`. It has `CapApp-SPM/` (Swift Package
Manager). CocoaPods was still installed because the community-plugin
ecosystem is transitioning — many plugins still require it. If future
plugins bundle SPM support, we may not need pod at all.

### Static export + backend URL
The current `NEXT_PUBLIC_API_URL=http://localhost:4000` in `web/.env.local`
is baked into the static bundle at build time. On a physical device or
release build, that URL is meaningless. Before the first real device test:
- **iOS simulator**: `localhost:4000` still works (simulator shares the
  host's network namespace).
- **Android emulator**: `localhost` from the emulator points at the
  emulator itself. Use `http://10.0.2.2:4000` (special alias for the host
  machine).
- **Physical device on same wifi**: use the host machine's LAN IP
  (`http://192.168.x.x:4000`) and make sure NestJS is bound to `0.0.0.0`
  not `127.0.0.1`.
- **Production build**: hosted backend URL. Rebuild required after
  changing — the URL is inlined.

Consider adding a `.env.production` for the release build so we don't
accidentally ship a build pointing at localhost.

runtime ~87.5 kB (React + Next runtime + Stripe). Per-page bundles are
1-3 kB except `/tenant/card` (~8 kB, Stripe Elements). All well within
what a mobile webview handles instantly.
